DuoLM: Fast and Effective Personalized Recommendation with Language Models

📅 2026-10-28

DeepMind等：DuoLM单卡吞吐提升60倍，推荐媲美专家模型？

一、引言

电商推荐和内容发现场景中，语言模型正成为个性化推荐的核心引擎。它能够利用丰富的物品内容、用户交互历史和显式反馈，评估哪些候选物品最符合个体偏好。然而，一个推荐请求往往需要同时评估多个候选物品，而系统必须在有限的计算预算内维持连续不断的请求流。这意味着，语言模型在推荐场景中的实际价值，不仅取决于推荐质量，更取决于服务效率。

论文指出了两个核心挑战。第一，在不牺牲推荐质量的前提下大幅压缩在线计算，并不容易。传统基于 ID 的双塔推荐器评分效率很高，但仅依赖交互数据训练，难以融入文本语义和预训练世界知识，对长尾和冷启动物品的泛化能力受限。全文本 cross-encoder 会同时使用物品描述、用户历史和反馈，但候选表示依赖用户上下文，无法跨用户直接复用。压缩物品文本虽能减少在线计算，却可能丢失对特定用户重要的细节。

第二，模型计算的减少并不会自动转化为端到端的请求加速。vLLM 等推理引擎通过批处理和前缀缓存提升吞吐，但推荐服务在准备工作负载时仍存在冗余。一个推荐请求通常让多个候选物品共享同一段用户历史，如果候选被分别提交，服务端就会反复构建和传输相同的历史输入，并为每个候选产生独立的调度开销。

DuoLM 正是针对这两个挑战提出的框架，它将表示学习与高效推理整合在一起：离线学习可复用的物品表示，在线只运行轻量排序器，并通过一系列运行时优化将计算节省转化为真实的服务吞吐。

二、核心方法

DuoLM 的核心思路可以概括为：让物品表示与个性化判断解耦，让历史计算在候选之间共享。

可复用的物品向量与连续输入接口

DuoLM 采用双 LLM 架构。编码器 LLM 负责将每个物品的模板化文本压缩为一个用户无关的隐藏状态向量，连续输入接口再将其映射为排序器可消费的单个连续嵌入：

$$\widehat{a}_{i}=\frac{a_{i}}{\sqrt{\operatorname{RMS}(a_{i})^{2}+\epsilon}},\quad z_{i}=\rho e^{\gamma}\,\widehat{a}_{i}$$

个性化排序器 LLM 接收混合输入：指令文本、历史条目（物品向量 + 反馈文本）、候选物品向量。每个候选物品在共享前缀后独立评分：

$$h_{q,j}=\big[B_{\theta_{B}}(P_{q}\oplus z_{c_{j}})\big]_{\mathrm{last}},\qquad s_{q,j}=w^{\mathsf{T}}h_{q,j}$$

这一架构的关键收益在于：物品向量与用户无关，可以离线预计算并跨请求复用；在线阶段只需运行排序器，而排序器的历史前缀在同一个请求的多个候选之间共享。由于评分直接读取候选位置的最终隐藏状态，整个排序过程不需要自回归解码。

端到端训练与教师蒸馏

编码器、连续接口和排序器通过推荐标签与教师蒸馏联合训练。教师模型是一个冻结的全文本模型，接收相同的指令、历史和反馈，但物品以原始文本形式出现，并在末尾附加评分后缀。教师先在训练数据上以交叉熵训练，然后冻结，并缓存其对训练用历史与候选组的原始打分。

学生模型的蒸馏损失让学生匹配教师在同一候选组内的偏好分布：

$$\ell_{\mathrm{KD}}(q)=\tau^{2}\sum_{j=1}^{K_{q}}p_{\mathrm{T},q,j}^{(\tau)}\log\frac{p_{\mathrm{T},q,j}^{(\tau)}}{p_{\mathrm{S},q,j}^{(\tau)}}$$

训练时物品向量在前向过程中重新计算，保留从打分模型经连续接口回传到编码器的可微路径。

高效推理：虚拟 ID、多候选评分与 CUDA Graph

训练完成后，学生模型冻结，物品向量被导出为 GPU 常驻表。每个物品被分配一个虚拟 token ID，嵌入查找时直接返回对应的预计算向量。在线请求因此只需携带物品 ID 和反馈文本，而不需要传输完整向量。在评分基准测试中，虚拟 ID 将平均请求负载减少超过 90%。

运行时层面的第二个优化是多候选评分（MIS）。同一个请求中的多个候选被拼接在共享前缀之后，运行时只构建和预填充一次用户历史，并在候选分支之间复用前缀 KV 缓存。通过树状注意力掩码，每个候选只能看到共享前缀和自身分支：

$$\mathcal{V}_{q}(a_{j})=\{0,\ldots,L_{q}-1\}\cup\{a_{j}\}$$

在精确算术下，MIS 的评分与逐个候选独立评分严格相等，但每层允许的 query-key 对数量从 $K_q \cdot L_q(L_q+1)/2 + K_q(L_q+1)$ 降为 $L_q(L_q+1)/2 + K_q(L_q+1)$，消除了 $(K_q-1)L_q(L_q+1)/2$ 组重复的前缀计算。

第三个优化是将 MIS 路径适配到分段 prefill CUDA Graph。运行时捕获 GPU 操作及其依赖关系，并在后续请求中回放，以减少 CPU 调度和 kernel 启动开销。

三、实验

论文在 Amazon Books 和 Video Games 两个数据集上评估了 DuoLM，骨干模型统一使用 0.6B 参数的 Qwen3。

推荐质量方面，DuoLM 在 Books 上的 NDCG@10 达到 0.5586，超过专家教师模型的 0.5440；在 Video Games 上为 0.5298，与教师的 0.5313 基本持平。评分预测任务中，DuoLM 的平均 NLL 为 0.9263，教师为 0.9233，两者非常接近；DuoLM 在期望评分 MAE 和 RMSE 上甚至略优于教师。

服务效率方面，在单张 H100、每个请求 100 个候选的设置下，DuoLM 的吞吐量从并发度为 1 时的约 8,870 候选评分/秒 提升到并发度 64 时的 26,400 候选评分/秒。与 vLLM 服务的教师模型相比，吞吐提升 22.7–60.1 倍；与 SGLang 服务的教师相比，提升 37.6–109.9 倍。在并发度 64 时，DuoLM 的 p99 延迟为 536.90 ms，而 vLLM 上的教师为 17,093.82 ms。

运行时归因实验进一步拆解了加速来源。在模型固定、请求轨迹固定的条件下，MIS 将吞吐量提升 4.81–29.3 倍，CUDA Graph 在此基础上再提供 1.06–3.54 倍 的加速。MIS 在较高并发度下收益更大，而 graph 回放对低并发场景的贡献更明显。

虚拟 ID 的诊断实验显示，与传输 FP32 向量相比，VID 将请求大小减少 99.0%，在并发度 8 时吞吐量提升 66.5%。仅将向量转为 FP16 虽然也能减小请求体积，但并不能稳定提升吞吐，说明减少传输字节本身并不足以保证更快的服务。

消融实验还给出了几个有实践价值的结论。物品读取方式上，直接使用编码器 EOS 位置的最终隐藏状态（LastToken）在 HR@1、HR@10、MRR@10、NDCG@10 四项指标上均优于增加可学习 memory token 或 Perceiver 查询的方案，且不引入额外参数，训练时间最短。反馈放置位置上，将反馈放在排序器（FIR）与放在编码器（FIE）质量相当，但 FIR 可以复用与用户反馈无关的物品表示，因此被选为默认配置。蒸馏策略上，CE+KD 联合训练将 Books 的 HR@1 从 0.3748 提升到 0.4024，NDCG@10 从 0.5502 提升到 0.5621；进一步增大蒸馏权重或温度反而会降低质量。额外的全文本自对齐不仅没有提升 NDCG@10，还将训练时间从 7.39 小时增加到 16.95 小时，因此未被纳入默认方案。

四、展望

DuoLM 展示了一条清晰的工程路径：将大模型推荐系统中的物品编码与个性化排序解耦，再通过虚拟 ID、共享前缀 KV 和 CUDA Graph 等运行时手段，把模型层面的计算节省真正转化为端到端吞吐。对于电商推荐、内容分发等需要在高并发下维持低延迟的场景，这种“离线表示 + 在线轻量排序”的架构具有直接的参考价值。

论文也坦承了当前评估的边界：实验集中在 Amazon Books 和 Video Games 两个数据集、0.6B 骨干模型，以及固定候选集上的评估。单向量压缩可能丢失对特定用户重要的细节，物品内容或编码器参数变化时需要重新生成离线表示。在更大模型、更多领域和真实检索候选分布下，这一框架的表现仍值得进一步观察。

当推荐系统越来越依赖大模型的理解能力，如何在质量与成本之间找到可持续的平衡点，或许比单纯追求更大的模型更值得思考。
