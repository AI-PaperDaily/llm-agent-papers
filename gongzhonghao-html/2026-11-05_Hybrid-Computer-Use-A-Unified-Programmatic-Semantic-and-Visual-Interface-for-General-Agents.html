Hybrid Computer Use: A Unified Programmatic, Semantic, and Visual Interface for General Agents

📅 2026-11-07

微软研究院联合复旦清华推出三通道Agent接口：平均得分72.37%！

一、引言

让Agent操作电脑，通常意味着反复截图、识别按钮，再用鼠标和键盘执行操作。简单任务尚可应付，一旦涉及长流程，定位控件、等待界面变化和确认结果，就可能消耗大量模型调用。

但电脑并不只有“看屏幕、点按钮”这一种操作方式：代码可以直接处理文件和数据，应用的无障碍接口也能暴露控件名称、状态及操作。如何让大模型根据任务灵活选择这些能力，而不是始终模仿人类操作？

微软研究院联合复旦大学、清华大学提出的Hybrid Computer Use（HCU），将程序化、语义和视觉交互统一到同一个Agent接口中。其重点不仅是增加工具，还包括压缩界面信息、批量执行操作，以及在切换通道时防止依据过期状态误操作。

二、核心方法

三通道接口：让模型自主选择观察和操作方式

HCU将三类能力放进同一个Agent上下文：

  • 程序化通道：使用Agent原有的代码、命令行和文件工具，直接处理数据或调用系统能力。
  • 语义通道：通过无障碍接口（Accessibility，简称AX）读取应用控件树，并按控件引用执行操作。
  • 视觉通道：通过图形用户界面（GUI）截图观察桌面，使用鼠标和键盘操作。

HCU通过模型上下文协议（MCP）为Agent增加AX和GUI工具；程序化工具则沿用Agent运行环境已有的能力。它不额外引入规划器或子Agent，而是让模型在原有的“观察—行动”循环中自行决定使用哪个通道。

观察与执行也不必经过同一通道。例如，模型可以先看截图理解界面布局，再通过AX定位输入框并填值；数据处理适合代码时，也可以转向程序化工具。

三种通道各有边界。AX依赖应用暴露的信息，自绘控件或尚未渲染的内容可能缺失；GUI覆盖面较广，却需要处理坐标和视觉定位。因此，HCU并不把语义操作设为强制路径，而是在结构化信息不足时允许模型请求截图。

Composable Semantic Interaction：压缩观察并组合动作

AX会提供包含角色、名称、值和状态的控件树，但原始树可能冗长，也可能包含大量结构性包装。HCU将保留的AX记录与展示给模型的精简视图分开：先给元素绑定目标引用，再压缩展示内容，同时保留记录用于目标识别和状态比较。未出现在精简视图中的目标，还可以通过查找或限定范围的观察获取。

拿到目标引用后，模型可以在一次调用中，对同一个应用窗口顺序执行多个已知动作，并插入可选的等待步骤。例如，先勾选复选框，等待其状态变为“已勾选”，再继续后续操作。等待步骤本身不发送输入，而是在条件满足后才放行后续步骤。

如果动作失败、等待超时，或者窗口连续性丢失，批次会在相应位置停止，并返回执行证据。这样模型不必盲目重做此前的动作。

调用结束后，HCU默认返回各目标的效果摘要和AX diff：相对上一次符合条件的观察，哪些值或窗口发生了变化。若这些信息足以支持下一步决策，就无需再单独调用观察工具；需要视觉确认时，模型也可以请求截图。

这里有一个关键区别：输入已发送，不等于预期效果已发生。HCU区分“确定没有发送输入”和“可能发送了输入、效果未知”，让Agent据此决定重试还是先检查状态。

Cross-channel Action Guards与Skill：检查状态并指导使用

三个通道操作的是同一台电脑，因此一个通道的动作可能使另一个通道持有的证据过期。例如，AX操作打开了弹窗，旧截图上的坐标就可能落到错误位置。

HCU在输入前设置两类保护：

  • AX目标保护：执行每个动作前重新解析引用，检查目标身份和操作条件；目标消失、被替换或存在歧义时拒绝输入，不自动转向同名控件。
  • GUI布局保护：坐标输入前，检查当前桌面边界、顶层窗口、堆叠顺序、活动窗口及目标点所在窗口等布局信息，是否仍与最近截图对应；发现变化时阻止输入并返回新截图。

这些检查针对当前状态进行，不论变化来自哪个通道，也覆盖批次中的逐个动作。它们降低了基于过期证据误操作的风险，但动作完成与否仍需要结合返回证据判断。

HCU还提供补充性的Skill使用说明：解释通道能力、目标引用、批量操作和等待步骤，并指导模型区分输入送达、局部界面变化与最终任务完成。该Skill不包含具体任务答案，主要用于减少工具调用和恢复过程中的常见错误。

三、实验

主实验使用OSWorld 2.0完整任务集，比较任务表现与资源消耗。其中，Partial是任务平均得分，Binary是获得满分的任务比例；主实验的步数上限为500步。

在同为GPT-6 Astra、同一Agent运行环境的对比中，HCU的Partial达到72.37%，高于CUA Driver的68.82%，即提升3.55个百分点；Binary从31.50%升至32.40%。两者每任务成本接近，分别为10.03美元和10.05美元，而HCU的工具调用次数减少29.81%。

使用Claude Opus 5时，HCU的Partial为72.06%，Binary为35.19%；相较该模型官方排行榜结果，分别提高3.75和3.76个百分点，每任务成本从28.43美元降至22.67美元。Partial和Binary的最优结果分别由不同模型取得；排行榜及其他系统结果的版本和评测条件也并非完全一致。

消融实验在OSWorld 1.0、GPT-5.4、100步上限下进行。完整HCU得分为65.59%，相比CUA Driver的62.30%提高3.29个百分点，步骤数从40.74降至28.60，每任务成本从5.65美元降至2.52美元。

去掉AX后，得分降至62.79%，步骤数升至33.28，说明在该配置下语义通道对表现和效率贡献较大。去掉GUI后，得分为66.08%，与完整HCU的差异处于运行间波动范围内，但步骤数增至32.16：视觉通道在这组实验中主要体现为交互效率上的补充。

Skill消融显示，加入使用说明后，因参数格式错误而被拒绝的AX和GUI调用占比从17.37%降至1.36%；完整配置的得分也比不使用Skill高1.59个百分点。

在OSWorld 1.0的四模型对比中，HCU相对CUA Driver均获得更高得分，增幅为2.94至12.90个百分点，成本降低8%至55%，但通道偏好明显不同：GPT-5.4的AX调用占其AX与GUI桌面调用的80%，Claude Opus 5.5则有94%使用GUI。Claude在HCU下总体步骤数接近不变、耗时增加6%；在两种配置都调用桌面工具的任务中，四个模型使用HCU的步骤数均减少19%至40%。
