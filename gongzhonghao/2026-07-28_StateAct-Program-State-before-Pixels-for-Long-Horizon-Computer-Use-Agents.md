# Salesforce研发出StateAct：基于程序状态而非像素的电脑Agent，成功率飙升26.9%，成本骤降9倍

## 引言

当你让AI帮你操作电脑时，它看到的和你看到的完全一样：一张截图。但截图的局限性远超想象：同一张表格可以显示相同的数字，背后却可能是公式、是四舍五入的结果，甚至是滚动出屏幕的数据。更糟糕的是，在长达数百步的复杂任务中，每一次“看错”都会像多米诺骨牌一样层层累积，最终导致任务彻底失败。

如何让AI Agent真正“理解”它正在操作的电脑，而不是简单地“看图识字”？来自Salesforce AI Research的研究团队给出了一个颠覆性的答案：**放弃像素，拥抱状态**。他们提出的**StateAct**架构，将Agent的主要交互接口从屏幕截图转向程序底层状态（文件、DOM、应用后端数据），同时保留一个专门的GUI子代理处理最必需的视觉交互。实验显示，StateAct在OSWorld 2.0基准上将Claude Opus 4.8的二进制成功率从20.6%提升至26.9%，部分成功率从54.8%提升至61.6%，同时将每任务成本从约72美元骤降至7.8美元——**成本降低9倍，性能反而更高**。

## 一、核心方法

### 1.1 两个通道的模型：为什么像素是“有损”的

研究者的核心洞察建立在一个简洁的形式化模型上。设 $s \in \mathcal{S}$ 为计算机程序状态（文件、应用后端、DOM、表格等）。Agent从未直接观察到 $s$，而是通过两个通道来观察：

- **像素通道**：$o_{\text{pix}} = f_{\text{render}}(s)$，即屏幕渲染结果
- **状态通道**：$o_{\text{state}} = g(s)$，即通过命令行、API调用等方式直接查询底层数据

两个关键的结构性事实支撑了整个方法：

$$
G(s) \neq \tilde{G}(f_{\text{render}}(s))
$$

也就是说，**任务的成败判断 $G(s)$ 不能从渲染结果 $f_{\text{render}}(s)$ 中可靠地恢复**。原因在于 $f_{\text{render}}$ 不是单射函数：不同的程序状态可能渲染出难以区分的截图。一个单元格显示“100”，但它是公式计算结果还是直接输入的值？隐藏的行或列中包含什么数据？这些对任务成败至关重要的信息，截图无法传达。

更可怕的是，这种信息丢失在单次操作中可能无所谓，但在数百步的长期任务中会逐级累积，最终导致灾难性偏差。相比之下，状态通道 $g(s)$ 在任务涉及的状态子集上是近乎可逆的——直接读取 `workbook["B7"].value`，Agent就能精确获得单元格的实际值。

![图2：StateAct整体架构](https://arxiv.org/html/2607.22798v1/x2.png)

### 1.2 混合动作空间：主代理负责状态，子代理负责屏幕

StateAct的架构由三个核心组件构成：

**（1）基于状态的主代理**：主代理的动作空间是代码和结构化操作：持久化bash、文件编辑器、图像查看工具、计划清单、完成操作和代理委托工具。主代理完全没有鼠标和键盘操作能力。它通过主动探测来发现程序状态：先利用预训练知识推测应用存储状态的方式（邮件存储、办公文档格式、浏览器配置文件等），再通过 `find`、`ls`、`grep`、`sqlite3` 等命令精确查找。

**（2）专用GUI子代理**：虽然主代理以状态操作为主，但并非所有操作都能通过代码完成。当一个子目标“本质上是视觉化的”——比如无法通过文件/后端/DOM路径定位目标、效果只能通过渲染交互表达（拖拽画布元素、关闭不可脚本化的弹窗、读取仅在屏幕上存在的值）——主代理会委托给专门的GUI子代理。实际使用率极低：**在108个任务中，仅有28个任务需要GUI子代理，占主代理步骤的1.1%**。

![图3：同一子目标通过不同通道执行的对比](https://arxiv.org/html/2607.22798v1/x3.png)

### 1.3 基于状态的验证与长期执行管理

**独立完成门（Finish Gate）**：当主代理调用 `finish` 时，一个完全独立的验证模型会启动。它的上下文只包含原始任务指令和机器访问权限（bash、文件读取、DOM查询），**从未看到主代理的消息历史、计划或完成理由**。这带来了四个关键特性：
- **叙述盲**：仅看任务和机器，不被Agent的“自夸”影响
- **状态基础**：在真实的持久化工件上检查结果
- **防捕获**：必须独立定位任务指定的交付物
- **有限纠正**：拒绝后允许主代理最多三轮修复

**上下文管理**：面对长达数百步的任务，StateAct采用三种机制：
- **新上下文专家**：每次委托都在独立上下文窗口中运行
- **自动压缩**：接近上下文限制时，对最早的内容进行摘要
- **外部化计划**：任务清单持久化在消息历史之外，每次轮次重新注入

## 二、实验结果

### 2.1 主实验结果

StateAct在同一条骨干网络（Claude Opus 4.8）上的表现令人瞩目：

| 配置 | 二进制成功率 | 部分成功率 | 每任务成本 |
|------|:-----------:|:----------:|:----------:|
| Opus 4.8 (CUA参考) | 20.6% | 54.8% | ~$72 |
| **StateAct (Opus 4.8)** | **26.9%** | **61.6%** | **~$7.8** |
| GPT-5.5 | 13.0% | 49.5% | ~$25.5 |
| Opus-4.7 | 18.2% | 48.9% | ~$33.6 |

StateAct不仅在性能上超越所有公开基线，更将成本控制在仅为最强竞争者的1/3到1/9。**性能提升与成本降低同时实现**，这在AI系统中极为罕见。

![图4：失败原因分析](https://arxiv.org/html/2607.22798v1/x14.png)

### 2.2 消融实验揭示的关键组件

研究者通过逐步移除组件，量化了每个创新点的贡献：

| 配置 | 二进制成功率 | 部分成功率 |
|------|:-----------:|:----------:|
| 完整StateAct | **26.9%** | **61.6%** |
| 移除验证门 | 23.1% | 57.5% |
| 移除上下文管理 | 21.3% | 58.7% |
| 移除状态动作 | 18.5% | 51.3% |

**状态动作是最核心的贡献**：移除后部分成功率直接跌破参考基线（54.8%）。纯代码（无GUI子代理）只能达到45.9%，这说明**状态操作并非万能，但它是提升长期任务执行能力的最优路径**。

### 2.3 失败分析：瓶颈从感知转向推理

对79个非完美任务的详细审计揭示了深刻的现象：

- **推理错误（38个任务）**：主导性失败模式——Agent错误理解了指令、得出了错误数值
- **验证门错误接受（14个任务）**：验证门接受了实际失败的结果
- **模态瓶颈（约20%的任务）**：需要音频、视频、实时交互等不可跨越的瓶颈
- **歧义指令（约20%的任务）**：任务描述有多个有效解读

关键洞察：**StateAct已经解决了绝大多数感知失败**。通过代码精确读取“单元格B7”或列出日历存储，感知误差几乎消失。验证门解决了持久化缺陷（文件丢失、路径错误、格式不匹配）。但两者的盲区都是**推理**——验证门无法判断数值是否正确，因为从同一来源重新推导会产生同样的错误。

研究者总结道：**“状态基础将准确性瓶颈从感知推到了推理；它没有消除瓶颈，只是转移了它。对于长期电脑使用任务，瓶颈现在是Agent在想什么，而不是它看见了什么。”**

## 三、展望

StateAct的研究不仅提供了一个高性能的Agent架构，更重要的是揭示了长期电脑使用任务的根本瓶颈转变。当Agent不再“看错”时，“想错”就成了主要挑战。这为后续研究指明了方向：如何构建不依赖真值标签但能验证数值正确性的系统？如何让Agent在数百步任务中保持推理的一致性？

或许，大型语言模型需要的不只是更好的视觉能力，而是更像程序员的思维方式：**始终直接操作状态，只在必要时才瞥一眼屏幕**。
